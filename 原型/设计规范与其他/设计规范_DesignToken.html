Design System · Token Standard v1.0

金蝶 OA · 全系统设计令牌标准

目标只有一句：让全站有一个品牌色真源，把现在流通的多套蓝收口成一套令牌，并让「换个皮肤」「加个白标」从改代码变成改变量。 唯一真源文件是 tokens.css；本页是它的可评审看板，所有色块都直接引用该文件，不另存色值。

立项口径：这是设计体系级立项，不在《消息中心_需求描述》范围内 —— 那份文档只约束消息中心改版。两件事并行推进、互不阻塞：消息中心改版照原计划验收，令牌标准化单独排期、单独验收。
品牌色 #1f6ad8 唯一真源 tokens.css 组件禁止硬编码 hex 换肤只改变量 命名语义化

01现状基线（迁移依据 · 不美化）

下面四个数字是这次立项的前提。它们说明：把 #1f6ad8 写成规范是起步，不是完成。真正的成本在第 06 节的第三步。

0
业务代码里 #1f6ad8 的命中数
本文件是「新立的法」，不是「已生效的法」
#409EFF
现网实际主色，来自 Element Plus 默认 --el-color-primary
不是我们的品牌色，是组件库的出厂色
≈47
全站流通的饱和蓝种类
没有任何一个品牌色 token 在管它们
11
Element Plus 派生档（hover/active/disabled/light…）
已编译成 rgb() 字面量，不跟随 primary 变量

为什么这是真项目而不是一次改色：第 4 个数字是坑。EP 的 light-3/light-5/light-7/light-8/light-9/dark-2 等档位在构建产物里已经被算成 rgb() 字面量， 所以「把 --el-color-primary 改成 #1f6ad8」之后，按钮悬停、禁用、浅底这些状态仍然是 #409EFF 的派生色，页面看起来「改了一半」。 必须逐档桥接变量（tokens.css 文末的 EP 桥接段），再按模块做视觉回归。

本次可复核实测（不完全依赖转述）：取仓库内两份最新前端构建产物（h5-20261109、test-20261109-oa-dev）做全文检索 —— #1f6ad8 命中 0；按「色相 195–250°、饱和度 ≥55%、亮度 ≥35%」判据去重，实测 68 种饱和蓝，比源码口径的 47 更多，多出来的是第三方组件与图表色。 结论不变、只会更重：收口规模只多不少。

05治理规则

令牌化失败从来不是「文件没写」，而是写了没人守。四条规则 + 三个能自动跑的验收手段，比任何文档都管用。

R1唯一来源

颜色/圆角/间距/字号只认 docs/tokens.css。组件、页面、原型里出现 #1f6ad8 这类字面量即视为缺陷，评审直接打回。

R2命名语义化

按「角色」命名，不按「外观」命名：写 --color-primary、--color-danger；禁止 --blue-500、--c1、--light-blue。

R3换肤只改变量

深色、主题、白标定制只允许改 tokens.css 里的值，变量名不动。禁止在组件里写 .dark .btn{} 这类条件样式，否则换肤立刻失控。

R4新色入册需评审

要加颜色，先改 tokens.css 并更新本看板，评审通过才算入册。评审要回答三个问题：属于哪一层？和现有哪个 token 重复？不新增会怎样？

5.1 三个可自动化的验收手段

手段怎么做拦什么
硬编码扫描 CI 里跑 grep -rniE "#[0-9a-f]{3,6}\b" src --include=*.vue --include=*.css --include=*.scss | grep -v tokens.css，命中数只允许下降不允许上升 新增硬编码色值
Stylelint 规则 color-no-hex: true（白名单只放 tokens.css）+ 自定义 declaration-property-value-allowed-list 限定字号/间距取值 PR 阶段就挡住
可视化回归 每个改动的页面截图与基线对比（已有 UI 测试链路可挂），批量替换时按模块出 diff 收口后的视觉偏移

06迁移三步（诚实的成本结构）

三步里只有第一步是「快」的。真正的工作量在第三步，而且它不是一个纯设计任务，需要开发、测试、产品一起排期。

步骤 做什么 工作量 / 风险 验收口径
① 立法 落 tokens.css + 本看板；不接任何现有页面，纯新增文件 小 · 零风险 文件合并即完成。此时线上没有任何变化，不需要回归
② 增量 新页面、新组件强制走 token；同时把 EP 变量桥接上（tokens.css 文末注释段） 增量零 · 中风险 新页面无硬编码 hex；EP 按钮实际渲染色 = #1f6ad8（DevTools 验证，不能只看代码）
③ 收口 老页面按模块分批替换：先消息中心、再审批流、再报表与后台；每批一次视觉回归 主要工作量 · 高风险 68 种饱和蓝（源码口径 47）逐模块归零；每批附截图 diff；不允许「一次全量替换」

必须写明的两件事（别让后来人以为这是件小事）：
① 现状是 68 种饱和蓝并存（源码口径 47）、且没有任何品牌色 token —— 收口等于一次全站视觉回归，不是改一个变量。
② Element Plus 的 11 个派生档已编译成 rgb() 字面量、不跟随 primary 变量 —— 只改 --el-color-primary 会出现「按钮主色变了、悬停和禁用没变」的半成品状态，必须逐档覆盖后再验收。

建议的排期姿势：步骤①②跟着本迭代走（成本极低）；步骤③单独排一个「视觉一致性」专项，按模块灰度、不与其他需求混在同一批回归里 —— 否则一旦出现视觉偏移，很难判断是功能改动还是收口引起的。

产品已确认范围（2026-11-11）：收口不是「待定」，而是明确要做。旧系统接手前没有设计，导致现在"一个地方一种蓝、花花绿绿"。方向已定：设计新 UI 一律走 token；旧界面色调渐进式分批换回统一主色 #1f6ad8，不在一期内硬切。任何"这里用一种颜色、那里用另一种"的散色，都归到本专项收口，不允许再新增第二套品牌蓝。

文件说明：本页与 docs/tokens.css 成对交付，看板通过 <link> 直接引用该文件，页面内不存第二份色值；改 tokens.css，看板自动同步。
与既有资产的关系：色值升格自 docs/消息通知_图标令牌表.html 已定稿的 :root 变量（#2b7fff / #2b6fd4 / #e2edff / #3aa655 / #ef9a3c / #f5453d / #909399 / #edf0f3 / #f2f4f7 / #a8adb5 等），一个未改，仅补派生档、结构量、语义化命名。
本次只新增两个文件（tokens.css、本页），未改动需求文档、notify_icons、图标令牌表或任何业务代码。
看板自身的说明性用色：本页说明框、外链提示、对比度结论标签用到少量排版色（如 #1e4b8a / #8a6a2a），属文档排版、不是产品 UI，未纳入 tokens；04 组件示例区已 100% 使用 token，无一处硬编码（自检时发现并补齐了 4 个缺失令牌：warning-text / danger-hover / skeleton / code-bg）。
待产品/开发确认项：① 主按钮白字达 AA —— 已确认：主色定为 #1f6ad8（5.10:1）；② --color-primary-disabled 的平色值是否符合现网禁用观感；③ --color-border-strong 是否统一到所有表单控件；④ 深色主题只在 tokens.css 里留了骨架，未做对比度评审，暂不启用；⑤ 通知图标「警」字形为 #ef9a3c on #fde6cd（1.86:1），是否在无障碍专项里改用 --color-warning-text；⑥ 旧界面渐进式收口（迁移第三步）已确认纳入排期，按模块灰度。
