本文件是设计效果稿，不是交付规格。数据取自 GET /oa_sys/business/user_account 实测返回的 6 个字段（id / account_no / account_name / bank_name / subbranch_name / remark）。 ⛔ 实测接口不返回 account_default，故「默认账户」徽标本轮无数据可显示，且全站不存在「账户管理」页 → 「设默认」无落点，本稿未画。 落地改动共 3 处单点：模板 width 1 行 + CSS height 1 行 + CSS padding 1 行（现状 height: calc(100vh - 236px) 是造成 522px 死白的唯一来源）。
⛔ Web 与 H5 不共用组件（H5 是 uni-app uni-popup，零代码共用），本轮不需要改 H5；「窄窗口降级」仅为 Web 侧窄视口 / 200% 缩放的防御性兜底。 ⛔ 本弹窗与合同关联弹窗共用同一批全局 CSS 类（.flow-select-container / .flow-list / .flow-item / .flow-item-choosed / .checkbox），任何结构改动必须加修饰类隔离，否则会串到合同关联弹窗。

为什么不再「竖下来排列」（机制已按 DOM 实测修正）
现状卡片根本没有网格，.flow-item 是 flex，渲染成两个独立纵向列：
列1 = [户名, 卡号, 银行]（3 个）｜ 列2 = [支行, 备注("")]（2 个，备注空串渲染为不可见）
→ 列 1 有 3 个、列 2 只有 2 个，右列先到头，视觉上就是「几行竖下来排列」，且第 3 行右侧空一整块。 这比「grid 某格换行」更贴你的原话 —— 「竖下来排列」= 字面意义上的两列竖排，「空空」= 右侧空白 + 下方 522px 纯白。
同时「银行」（字典选）与「支行」（手打网点名）语义矛盾，把字段凑成 5 个挤在两列里，越挤越竖。
修法：合并「银行+支行」→ 单字段「开户行」（值 = subbranch_name || bank_name，展示层拼接、零迁移） + 重排为 2×2 定尺网格（户名｜卡号 / 开户行｜备注）→ 矛盾字段对、竖排、右侧断裂、2×2 填不满，四件事一次解决。
CSS 实现口径（一个必须避开的算术坑）
.flow-item--bank{display:grid;grid-template-columns:232px 223px;column-gap:24px} + .flow-item--bank > .flow-item-col{display:grid;grid-template-columns:64px 1fr}
⛔ 不要写成 4 列：grid-template-columns:64px 168px 64px 159px 配 column-gap:24px 会生成 3 个 gap，字段区变 527px、弹窗变 655px —— 直接算错。上面「2 列 + 列内 2 列」的写法天然只有 1 个 gap。

尺寸跳变：是改造后才有的问题，不是现状问题
现状弹窗恒定 732px（height: calc(100vh - 236px)，与账户条数无关）， 所以现状没有跳变；改成内容自适应后才会出现「打开 732 → 收敛到 234」的跳变。 缓解：骨架屏阶段锁定 min-height → 200ms 高度过渡 → max-height: min(72vh, 620px) + flex 分层 + footer 吸底 → 取消顶部对齐改回垂直居中（否则短弹窗吊在上面更怪）→ prefers-reduced-motion 关过渡。
可承诺的稳定边界：同一条数据重复打开高度一致；列表内部滚动时容器高度不变；footer 相对位置稳定。 不承诺不同数据量下高度相同 —— 那是内容自适应的必然代价。

607px 是硬下限，不是审美值

  • CSS Grid 的 4 个列位跨行共享 → 值列宽 = 该列各行内容的最大值。
  • 值列1 = max(户名 112, 开户行 168) = 168；值列2 = max(卡号 159, 备注 112) = 159。
  • 网格 = 64+168+24+64+159 = 479（标签与值之间无间隙，只有两对之间有 24px 列组间距）。
  • 607 的完整口径：16(列表左) + 16(列表右) + 2(卡边框) + 36(卡左 = 8 竖条 + 20 ✓槽 + 8 起点) + 479(网格) + 44(操作区) + 14(卡右余量) = 607。
  • 若按「每行独立定尺」算成 547px，户名 3 字与 8 字的两张卡卡号列起始 x 不同 → 纵向扫卡号会跳列，2×2 可扫视的核心价值就没了。
  • 现状之所以「散」，是因为它根本没有网格（.flow-item 是 flex，两列各按内容宽度撑开）→ 换成 grid 是本方案最实质的一处改动。
  • 另有一个 608px 变体（标签列 50 + 值列等宽 168/168 + 操作区 64）：比本稿宽 1px、两列右端更齐。本稿取 607 / 标签 64 / 值 168+159 / 操作区 44，因为 44px 已满足 WCAG 2.2 的 24×24 命中区门槛，64px 属宽裕值而非必需。
⚠ 生产代码级：4 个线上级高危缺陷（比排版更该优先进排期，因为它们会写出错误数据）
① 列表最多 10 条：flagGet 不传分页 + has-more 直接置 false ⇒ 第 11 条起账户根本拿不到。 不修这个，「5 条全显 / 20 条搜索 / sticky 计数条」整套 IA 都无从验证。
② 「确定」未选中不禁用：oe() 无条件 emit('update:selected', V.value)，而 V 初值 {} ⇒ 用户没选就点确定，父表单的账户被清空。
③ 删除已选中账户后不清选中态：用户接着点确定 ⇒ 提交一个已被删除的账户（比绑错户更糟：绑了个不存在的户，下游付款才炸）。
④ 删除无二次确认、一键直删，且删除图标是 ElIconClose（与弹窗关闭「×」同形）⇒ 误触即永久删除、不可恢复，且形状歧义。本稿已改 trash 图标 + 加 Popconfirm。
另有 3 项 a11y 硬失败：div.flow-item 无 tabindex / role / keydown ⇒ 纯键盘用户无法选中、无法编辑、无法删除（WCAG 2.1.1 键盘可达硬失败）； 选中态现状只有颜色一个信号（WCAG 1.4.1 硬失败）；图标按钮无 aria-label。本稿的四通道 + radiogroup + roving tabindex 即为修这些硬伤。

行为口径（已按你的选择定稿）

  • 单选。1 条时打开即自动选中，仍需点「确定」才回填。
  • 新增后不自动选中（按需求原文）：新卡打「新建」chip + 滚动到可见 + toast「已添加，请在下方点选」。
  • 模型 C：增 / 删 / 改即时落库，只有「本次选择」是暂存态。footer 常驻 12px 微文案 「本弹窗内的添加 / 编辑 / 删除会立即保存」。
  • 删除已选中的账户 → 清空选中态 + 提示重新选择，不自动交给邻居（避免静默改变提交对象）。
  • 「确定」未选中必须 disabled —— 现状不禁用会清空父表单账户，这是必修缺陷，不是体验建议。
  • 1 条时打开即自动选中，且不允许取消（单条没有「比较」语义，取消只会把用户引进死路）。
  • 删除二次确认文案：「确认删除该银行账户？删除后不可恢复。若该账户正被选中，删除后需重新选择。」
