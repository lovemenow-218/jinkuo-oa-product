## 三、验收口径（写用例按此）

- **权限负向账号**：一律用 staff2 `18006931939`（test `sy-org-staff`）。主账号 `15060038842` 在 test 是 `sy-org-admin`，会让「应 403」永远成功。
- **403 / 404 场景**：无 `sy-org-admin` 门店关系查台账或导出（403）；`business_id` 指定无权门店（403）；查看无关单据详情（404）；非本单会计确认（403）。管理员或申请人身份**不能**确认；批量确认逐笔复核会计身份。
- **断言写法**：业务错误体**没有 `code` 字段**，需同时判 HTTP status 与 `success/status`；HTTP 200 但 `success:false` 也算失败。409（原审批事实缺失 / 单据失效 / 申请人收件关系变化）不能仅重试覆盖。
- **参数校验缺口**：`business_id` 传非正整数/非数字时服务端「不加门店筛选」，可记一条。
- **已读**：按接口口径（结论 5），详情失败不标已读；单条通知与预警详情都成功读取后才调 `/read`。
- **批量确认**：`record_ids` 1–100、逐笔独立、单笔失败不回滚；必须逐条检查 `results[].confirmed`，不能仅凭 HTTP 200 判定全成功。
- **档位实测反推**（结论 6）：依赖「发送预警」按钮 + 新版 Worker 上线才能造出多档位数据；以 `docs/预警档位明细_一年.csv`（RULE_VERSION=v2、GATE=40）为基线逐条比对 `events`，不一致即提缺陷。
- **导出**：接口层验 JSON 结构、筛选/排序联动、50000 行超限 400；产物层验 .xlsx 文件名与列完整性（结论 4）。

## 五、环境与测试前置（硬约束）

- 契约 §6 自述：**2026-11-09 测试环境新版候选曾短暂上线，因数据库结构缺口回退到旧版**；独立测试环境 Worker 仍是旧版，真实账号 PC/H5 验收尚未完成。实测前须先确认目标环境 **OA API / 数据库迁移 / 独立 Worker / 前端** 四者版本，否则用例结果不可采信。
- **没有面向客户端的「发送预警」接口**：事件由合格单据办结后的本单扫描 + 独立 Worker 每天北京时间 10:00 后扫描写入。若 Worker 未运行，台账实时阶段仍会变化，但不会自动产生当天通知。
- 台账在合格备用金单据**办结时即形成一单一行**，即使尚未产生提醒也会出现；`stage` 不等于当天是否实际产生过通知。
- 路由 `:id` 两套含义**不可混用**：通知接口 = 通知 ID；预警管理接口 = OA 流程单据 ID（`record_id`）。
- 读台账或详情**不会**标记消息中心通知已读。
