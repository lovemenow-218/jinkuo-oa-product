## 缺陷 1：服务端不校验必填字段

| 项    | 内容                                                                                    |
| ---- | ------------------------------------------------------------------------------------- |
| 严重度  | 高（前端校验可绕过，API 直连可造脏数据）                                                                |
| 接口   | `POST /oa_sys/business/oa_flow_record`（发起审批）                                          |
| 现象   | 模板中标记为必填的控件缺失时，服务端**照样创建成功**，不返回任何错误                                                  |
| 复现方式 | 测试环境 - h5 - 审批 - 发起审批 - 必填控件缺失仍创建成功｜① UI：用 `lhlh-金额数值` 模板（金额、数量均必填）发起审批，必填项留空提交 → 仍创建成功 ② 接口：`POST /oa_sys/business/oa_flow_record`，`content={}` → 200（应 400） ③ 用例：`tests/h5/test_flow_lifecycle.py::TestTemplateAndStart::test_submit_missing_required` |
| 证据   | 多次实测，缺必填字段的提交均返回 200 并生成记录 ID                                                         |
| 影响   | 仅靠前端拦截；绕过前端（脚本/接口调用/旧客户端）会产生**没有审批人的审批单**，流程卡死                                        |
| 建议   | 服务端按模板 widget 的 `required` 做兜底校验，缺失返回 4xx + 明确错误信息                                    |
| 监控用例 | `tests/h5/test_flow_lifecycle.py::TestTemplateAndStart::test_submit_missing_required` |

## ~~缺陷 2：登出后令牌仍然有效~~ ✅ **已修复（2026-11-17 验证）**

> 2026-11-17：`test_logout_invalidates_token` 在 regression 里由 XFAIL 转 **XPASS**，
> 探针复验——同账号开两个会话 A/B，`logout(B)` 返回 200 后 `B` 的 GET 立刻 **401**，
> 而 `A` 仍 200 ⇒ 登出**只作废本次会话的令牌**（不是全局踢人），符合预期。
> 原 xfail 已摘除，转为常规断言长期守护。

| 项    | 内容                                                                                                |
| ---- | ------------------------------------------------------------------------------------------------- |
| 严重度  | 高（安全）                                                                                             |
| 接口   | `POST /base_passport/logout` → 再用同一 token 访问任意受保护接口                                               |
| 现象   | 修复前：登出返回 200，但**旧 token 仍可正常访问**受保护接口。现状：旧 token 立即 401                                              |
| 复现方式 | 测试环境 - h5 - 登录/会话 - 登出后旧令牌仍有效｜① UI：登录 → 退出登录 → 用旧会话重放任意受保护页面 ② 接口：登录取 `token_access` → `POST /base_passport/logout`（200）→ 用同一 token `GET /oa_sys/business/oa_flow_record?tag=wait` → 仍 200 ③ 用例：`tests/h5/test_session_and_misc.py::TestSessionLifecycle::test_logout_invalidates_token` |
| 影响   | 用户退出后，令牌如果被截留（共享设备、日志、代理）可继续操作账号。测试清单 §1 明确要求"退出后访问审批页与提交接口被拦截"                        |
| 建议   | JWT 增加服务端失效机制（黑名单/版本号）；或缩短有效期 + 登出时清 refresh token                                                |
| 监控用例 | `tests/h5/test_session_and_misc.py::TestSessionLifecycle::test_logout_invalidates_token`          |

## 缺陷 4：任意员工可读取他人的审批详情（越权读）

| 项    | 内容                                                                                              |
| ---- | ----------------------------------------------------------------------------------------------- |
| 严重度  | **高（数据泄露）**                                                                                     |
| 接口   | `GET /oa_sys/business/oa_flow_record/{id}`                                                      |
| 现象   | 与记录**完全无关**的员工（不是发起人、不是审批人、不是抄送人）请求详情，返回 200，且**包含完整表单 `content`**                              |
| 复现方式 | 测试环境 - h5 - 审批 - 审批详情越权读｜① UI：次账号（陈林，staff_id 15774）打开主账号（陈林航，15751）发起、且审批人只有主账号的单据详情 → 可见完整表单 ② 接口：次账号 `GET /oa_sys/business/oa_flow_record/{id}` → 200 + 完整 `content` ③ 用例：`tests/h5/test_flow_cross_person.py::TestAuthorization::test_unrelated_user_cannot_read_detail`；web 侧 `tests/web/test_web_regression.py::test_W_REG_04_other_staff_cannot_read_my_flow_record`（xfail） |
| 证据   | `status=200`，`data.content = {"INPUT_...": "..."}`，`flow_status` 一并可见                           |
| 影响   | 同一企业内任一员工可拉取全部审批单的表单内容（金额、事由、个人信息）。审批系统里这属于**横向越权**                                             |
| 建议   | 详情接口校验「发起人 / 审批人 / 抄送人 / 流程管理员」身份，否则返回 403；至少对无关人员脱敏 `content`                                  |
| 监控用例 | `tests/h5/test_flow_cross_person.py::TestAuthorization::test_unrelated_user_cannot_read_detail` |

### ✅ 2026-10-15 已在 web 侧复验：**同样存在 → 影响面升级为「全平台」**

| 项    | web 侧实测结论                                                                                       |
| ---- | ----------------------------------------------------------------------------------------------- |
| 前提   | 两个账号 staff_id 不同（15751 / 15774），同为 `sy-org-staff`、同门店 200242                                    |
| 现象   | `GET /oa_sys/business/oa_flow_record`（web 端列表）两个账号各返回 12 条，**id 集合完全一致**                        |
| 关键点  | **web 端没有独立的详情接口**——列表每条直接自带 `content`（表单内容）与 `logs`（审批流水），**列表即详情**，所以"列表没过滤"等于"详情也没过滤"        |
| 结论   | 员工B 看到的 12 条**全部是员工A 发起**的单据，且含完整表单内容 → 横向越权在 web 侧同样成立                                         |
| 对照组  | 同一套账号下 `oa_flow_msg`（抄送消息）的 id 交集为 **0**，说明后端**具备**按人过滤的能力，本接口只是没做                              |
| 监控用例 | `tests/web/test_web_regression.py::test_W_REG_04_other_staff_cannot_read_my_flow_record`（xfail） |

## 缺陷 5：已办列表不按身份过滤（越权列）—— 已扩展为四个标签，见缺陷 6

| 项   | 内容                                                              |
| --- | --------------------------------------------------------------- |
| 严重度 | **高（数据泄露）**                                                     |
| 接口  | `GET /oa_sys/business/oa_flow_record?tag=manage`                |
| 现象  | 返回的记录里**大量与登录人完全无关**：既不是发起人、也不在任何一条审批轨迹里                        |
| 复现方式 | 测试环境 - h5 - 审批 - 已办列表不按身份过滤｜① UI：次账号（从未审批过任何单）打开已办/管理列表 → 全是主账号发起的单 ② 接口：次账号 `GET /oa_sys/business/oa_flow_record?tag=manage&limit=50` → 200 + 50 条，发起人全部是主账号 ③ 用例：`tests/h5/test_flow_cross_person.py::TestAuthorization::test_manage_list_only_related_records`（完整版见缺陷 6 / `scripts/probe_gaps.py`） |

**证据（三条互相印证）**

1. **两个账号拿到的列表一模一样** —— 这条最硬：
   ```
   主账号 manage：50 条，前 5 个 id [24643, 24642, 24641, 24640, 24639]
   次账号 manage：50 条，前 5 个 id [24643, 24642, 24641, 24640, 24639]
   两者重合：50/50 条（连 id 和顺序都相同）
   ```
   两个不同的人，「我处理过的」列表完全相同 → 这个 tag 根本没按登录人过滤，等同于返回全表。
2. **逐条查审批轨迹，次账号一次都没参与**：抽查前 10 条的 `logs`，审批轨迹人员全是  
   `15751`（主账号自己），次账号 `15774` 参与过 **0 条**。  
   发起人分布 `{'陈林航': 50}`。
3. **对照组**：同一个接口只差 `tag` —— `tag=wait` 返回 **0 条**（过滤正常）。  
   一个过滤一个不过滤，说明 `manage` 是遗漏而非设计取舍。

> ⚠️ 判定「无关」时不能只看 `flow_eids`：它只含**当前待审批人**，已经审完的人不在里面。  
> 必须查详情的 `logs` 才能确认某人是否参与过。这一点我们第一版判定踩过坑，已修正。

| 影响 | 配合缺陷 4，任一员工可遍历全公司审批数据 |  
| 建议 | `tag=manage` 与 `tag=wait` 采用同一套身份过滤（我发起 / 我审批过 / 抄送给我） |  
| 监控用例 | `tests/h5/test_flow_cross_person.py::TestAuthorization::test_manage_list_only_related_records` |

**手动复现（只要一个账号，最简单）**

用**次账号**（陈林 18006931939，从未审批过任何单）登录 H5 → 打开「已办 / 我处理过的」列表。

- **预期**：列表为空（他什么都没处理过）
- **实际**：能看到别人的全部审批单

接口层对照（F12 Console，token 从任意请求的 `Authorization` 头复制）：

```js
// 已办：不过滤 —— 返回 50 条，发起人全是别人
fetch('/oa_sys/business/oa_flow_record?tag=manage&limit=50',
      {headers:{Authorization:'Bearer xxxxx'}})
  .then(r=>r.json()).then(d=>console.log('已办', d.data.length))

// 待办：过滤正常 —— 返回 0 条（同一个接口，只差 tag）
fetch('/oa_sys/business/oa_flow_record?tag=wait&limit=50',
      {headers:{Authorization:'Bearer xxxxx'}})
  .then(r=>r.json()).then(d=>console.log('待办', d.data.length))
```

同一个接口 `tag=wait` 过滤、`tag=manage` 不过滤，这一对照最能说明是遗漏而非设计。

## 缺陷 6：四个审批列表标签集体不做身份过滤（缺陷 5 的完整版）

| 项   | 内容                                                              |
| --- | --------------------------------------------------------------- |
| 严重度 | **高（数据泄露）**                                                     |
| 接口  | `GET /oa_sys/business/oa_flow_record?tag=`                      |
| 现象  | 六个标签里 **manage / send / copy / msg 四个都不按登录人过滤**；只有 wait、done 正常 |
| 复现方式 | 测试环境 - h5 - 审批 - manage / send / copy / msg 四标签不按身份过滤｜① UI：主账号处理完一条单，次账号（从未参与）依次切四个列表 → 都能看到主账号记录 ② 接口：次账号 `GET /oa_sys/business/oa_flow_record?tag=` 依次传 manage、send、copy、msg → 含他人记录；wait、done 为正常对照组 ③ 脚本：`.venv/bin/python scripts/probe_gaps.py --env=test`（第 3 节打印六标签对照表）；用例：`tests/h5/test_flow_gap_lists.py::TestTagIdentityFilter`（6 条，4 条 xfail） |

| tag    | 语义   | 主账号 | 次账号   | 结论   |
| ------ | ---- | --- | ----- | ---- |
| wait   | 待我审批 | 无   | 无     | ✅ 正常 |
| done   | 我已办  | 有   | 无     | ✅ 正常 |
| manage | 已办   | 有   | **有** | ❌ 泄漏 |
| send   | 我发起的 | 有   | **有** | ❌ 泄漏 |
| copy   | 抄送我的 | 有   | **有** | ❌ 泄漏 |
| msg    | 消息   | 有   | **有** | ❌ 泄漏 |

**最强证据**：四个标签在两个账号下返回的 id 集合**完全相同（50/50，连顺序都一致）**，  
且与 manage 的集合相等 —— 说明它们走的是同一个未过滤的查询分支。

另外验证了抄送本身是生效的：模板抄送节点送达后，次账号的 `copy` 和 `msg` 里确实有该记录，  
只是**列表没有按收件人过滤**，所以「有抄送」和「看别人的」混在一起。

| 影响 | 任一员工可读到全公司所有审批单（含表单金额、明细、附件），且四个入口都能翻 |

> 2026-10-27 实测确证。用户反馈：「金额和明细 外面只显示金额数字，

| 复现方式 | 测试环境 - h5 - 审批 - 表头金额≠明细合计仍可提交｜① UI：用含 `MONEY_*` 表头 + `DETAIL_*` 明细的模板，表头填 500.00、明细填 60+40=100.00 → 提交成功 ② 接口：`POST /oa_sys/business/oa_flow_record` 带上述不一致金额 → 200，两值原样入库、无报错无告警 ③ 脚本：`.venv/bin/python scripts/probe_amount_detail_check.py`（逐组实测见本条「实测」表） |

### 实测

探针 `scripts/probe_amount_detail_check.py`（模板 id 6953，控件 `MONEY_TOTAL` +

| 不一致（表头大） | 500.00 | 100.00 | 200 ✅ | 500.00       |
| 不一致（表头小） | 10.00  | 100.00 | 200 ✅ | 10.00        |

⇒ **服务端对"金额 = 明细合计"零校验**，一致与不一致行为完全相同。

**① h5 端审批详情页明确不渲染明细**（`pages-oa_sys-flow_detail-*.js`）：

```js
// 轨迹里的表单快照：DETAIL_ 前缀的控件 → 渲染空
```

**② web 端只在"查看"态显示明细表格，且自动加合计行**（`flow-detail-l9IgI8Dg.js`）：

```js
tableMap(o){ ... if (行内含 MONEY_/NUM_) rows.push({...rows[0], isTotal:u}) }   // 追加合计行
```

注意：合计行是**前端按明细行现算**的，**不会与表头金额做比对，也不会标红差异**。

**③ web 端在"日常费用报销"模板下会按 CASCADE 维度分组汇总**（`flow-detail-BTxK3ugo.js`）：

```js
if (flowName.includes("日常费用报销") && 有 CASCADE 子控件) {
```

同样是**只展示、不校验**。

| 影响   | ① 员工填错金额不会在提交时被拦，需人工二次核对；            |
|      | ② h5 审批界面看不到明细，审批人**只看到表头一个数字**，无法核对；   |
|      | ③ 汇总与明细口径分离（web 有合计行、h5 无明细），两端对账口径不一致。 |

|      | ② 服务端必须兜底（前端校验可绕过，API 直连可造脏数据）；         |
|      | ③ h5 审批界面补渲染 DETAIL 明细（现在直接渲染空）；             |

## 需求建议（非缺陷）：@ 通知的最终形态 —— 新增「通知」tab 页

> 2026-10-27 用户给出明确方案。缺陷 33 已确证「评论 @ 人不产生任何通知」，
> 用户在此基础上给出了**产品侧的落地方案**，本节把方案固化成可实施的需求描述。

**用户方案原文**：「当前流程缺少材料时审批不驳回选择在评论中 @ 相关人员补充材料，
加个信息通知 or 考虑如何添加 → **@ 新增通知 tab 页，卡片显示谁通知谁，详情内容是流程**」

### 场景（发起方的真实痛点）

流程走到一半，审批人发现**材料不齐**，但此时驳回会让申请人重走流程。
期望：审批人**不驳回**，在评论里 **@ 申请人**请其补充材料，申请人**立即收到通知**，
补完材料后流程继续。当前这一步**断在"评论 @ 人不产生通知"**（缺陷 33）。

### 方案拆解

| 要素     | 方案                                                                 |
| ------ | ------------------------------------------------------------------ |
| 入口     | 消息页**新增「通知」tab**（当前线上只有 wait/done/create/cc/budget 五个）           |
| 卡片内容   | **显示谁通知谁**（如「陈林航 通知 陈林」）+ 通知来源摘要 + 时间              |
| 详情内容 | **详情展示流程内容**（进入被 @ 的那条单据详情页，而非跳到一个空的通知列表）      |
| 触发动作   | 评论中 @ 人（cmd=14）时生成一条通知                                |
| 数据要求   | 评论载荷必须带**被 @ 人的 id 列表**（现状只传 `@姓名` 纯文本，见缺陷 33 根因）     |

### 与缺陷 33 的关系

缺陷 33 是**问题定义**（为什么现在收不到）；本节是**方案定义**（应该收到什么、收在哪）。
两者配套：方案落地后，缺陷 33 的监控用例（3 条 xfail）会自动 XPASS。

**实现要点提示**（供开发参考，非测试要求）：

1. **载荷优先**：评论接口增加 `mention_eids: [staff_id...]`，比解析 `@姓名` 文本可靠
   —— 本环境主账号「陈林航」正好是次账号「陈林」的**前缀**，文本匹配极易误伤。
2. **通知与抄送分开**：`cc` tab 的语义是"流程抄送"，通知是"点对点提醒"，
   建议独立 tab，不要混用，否则 `cc_count` 的语义会被污染。
3. **详情跳转**：通知详情应指向**被 @ 所在的那条流程单据**，且被 @ 人对该单据应可见
   —— 这要求单据可见性口径把"被 @ 人"也算进去（当前按 wait/done/create/cc/budget 过滤，
   被 @ 人不在任一集合里，需新增可见性规则）。
4. **幂等**：同一条评论重复读取不应重复生成通知。

### 待确认 1：提交接口无幂等

- 现象：同一份数据连续提交两次，产生**两条**记录（ID 不同）
- 风险：弱网双击、超时重试会重复发起审批
- 需确认：防重是只做在前端，还是需要服务端加幂等（建议：表单提交带幂等键）
- 现状：用例固化当前行为（断言"产生两条"），规则变更后需同步更新

### 待确认 2：金额与日期不校验合法性

以下输入服务端**全部接受**并原样存储：

| 输入                           | 场景    | 是否合理   |
| ---------------------------- | ----- | ------ |
| 金额 `-100`                    | 借款/报销 | 通常不应为负 |
| 日期区间开始 > 结束（如 10-31 → 10-01） | 请假区间  | 通常应拒绝  |
| 不存在的日期 `2026-02-30`          | 单日期控件 | 通常应拒绝  |

- 需确认：这些校验是否应放在服务端

### 待确认 3：待办角标是"未读数"而非"待办总数"

- 现象：`GET /oa_sys/business/oa_flow_recordcount` 的 `wait_count` 在**拉取过详情后清零**（3→0），但待办列表仍有全部记录
- 需确认：角标语义是"未读"还是"待办总数"？若产品预期是总数，则属缺陷

### 待确认 4：会签节点允许同一人重复审批（轨迹失真）

> 先说结论修正：上午用单账号推断过「`multi=2` 是会签且按人去重」——**那个结论是错的**。  
> 有了第二个账号后实测，两种配置的真实语义如下（判定依据：两人节点，让其中一人单独审批）：

| 配置                            | 真实语义            | 实测表现                             |
| ----------------------------- | --------------- | -------------------------------- |
| `multiInstanceApprovalType=2` | **或签**：任一人通过即完成 | 两人节点，任一人单独审批 → 直接终态，与顺序无关        |
| `multiInstanceApprovalType=1` | **会签**：所有人都要通过  | 两人节点，单人审批 → 仍审批中；两人都审 → 终态，与顺序无关 |

**两种语义都正确**，不是缺陷。上午判断错的原因是：当时把下一级节点指派给一个无法登录的  
第三人，我第二次审批被拒其实是「我不是下一级的审批人」，而非「会签未满足」。

保留的疑问是**会签（multi=1）下同一人重复审批会被接受**：不推进流程，但会在审批轨迹里  
多出一条同一人的「通过」记录，看起来像多人审过。

- 影响：审批轨迹失真，审计时可能误判为"多人已审"。当前可见的 86 个审批节点里 82 个是  
  `multi=1`（会签），主流配置正好落在这一种上。
- 需确认：是否应拒绝同一人的重复审批？
- 监控用例：`tests/h5/test_flow_countersign.py::TestCountersign::test_duplicate_approval_rejected`

### 待确认 8：办理节点的 jkType 决定是否强制「付款凭证科目」（2026-10-10 新定位）

之前一直以为「办理走不到终态」是环境缺能力（钉钉付款凭证接口 404）。对照实验后发现

## 缺陷 23：档案 `action` 枚举无守卫
