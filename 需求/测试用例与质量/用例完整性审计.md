## 7. 多人审批节点（会签）、抄送与长流程覆盖（2026-10-10 补）

> ⚠️ **本节中的语义结论已被 §8 推翻**（同级日下午拿到第二账号后的实测为准）。
> 单账号手法本身没错（它帮助我们发现了盲区），但它**无法区分**「会签未满足」和
> 「我不是下一级审批人」两种情况 —— 两者都表现为"我的审批被拒"，因此误判了 `multi` 的含义。
> 保留本节是为了记录这个坑：**双人验证不可替代**。正确语义见 §8。

**起因**：用户提供的一条生产流程——

```
发起(周静) → 审批[沈逸] → 审批[沈逸,黄桦] → 会计审批[福军,蒲文,小妹]
          → 审批[小妹,汪宇] → 审批[汪宇,廖欣] → 出纳办理[廖欣,婷婷]
抄送：朱鹏丽、沈逸
```

6 个节点里 5 个是**多人节点**（界面文案「需所有人…同意」）。而我们此前的自动化模板
全部是单人节点（assignees 只有登录人自己）——**这条真实流程实际上跑不到**。

**单账号下如何测会签**（关键手法）：把「下一级」节点指派给一个**别人**的 staff_id
（该人不需要能登录）。于是：

- 当前节点未完成 → 我再审批，服务端以「不能操作」拒绝，流程状态不变
- 当前节点已完成 → 流程前移到下一级（审批人是别人），我再审批同样被拒

用「第 2 次审批是否被接受 + 状态是否变化」即可判定多人节点的完成条件。

**~~实测语义~~（已被 §8 推翻，仅作历史留档）**：

| 配置 | 单人通过能否推进 | 同一人重复审批 | ~~结论~~ |
| --- | --- | --- | --- |
| `multiInstanceApprovalType=2` | 不能 | 被拒「不能操作」 | ~~会签，按人去重~~ → 实为**或签** |
| `multiInstanceApprovalType=1` | 不能 | **被接受** | ~~不去重~~ → 实为**会签**，不去重这条是真的 |

### 会签与或签的最终语义（`tests/h5/test_flow_countersign.py`，11 条）

- **或签**（`multiInstanceApprovalType=2`）：两人节点中任一人通过即完成 → 流程终态；
  终态后另一人再审批被拒（终态保护生效）。
- **会签**（`multiInstanceApprovalType=1`）：只一人通过时保持审批中；双方都通过才终态；
  顺序无关（次账号先审仍需主账号补审）。
  - ⚠️ 会签下**同一人重复审批当前仍被接受**（xfail 监控）。真实双人场景下两人各审一次会正常终态，
    所以风险低于早先单账号推断；但接口层缺少按人去重，仍是隐患。
  - 线上 86 个审批节点里 82 个是 `multi=1`，即主流配置就是会签。
- 6 级长流程（与用户生产流程等长）：6 次审批后终态，中间保持审批中。
- 抄送节点不阻塞流程；`jkType=0` 审批节点可正常终态。

## 9. 会计审批与出纳办理（2026-10-10 补）

用户给的 production 流程里有两个角色化节点，此前均未覆盖到位：

```
→ 会计审批[福军,蒲文,小妹]   界面「待会计审批 / 需所有人会计审批同意」
→ 出纳办理[廖欣,婷婷]       界面「待出纳办理 / 需所有人出纳办理同意」
```

### 关键突破：办理节点的 jkType 才是那把钥匙

「办理走不到终态」此前一直被当成环境缺能力（钉钉付款凭证接口 404）。对照实验证明
（`scripts/probe_transact_block.py`）真正原因在**节点本身的 jkType**：

| 节点配置 | 办理结果 |
| --- | --- |
| `type=5, jkType=0` + `usebank=0` | ✅ 200 |
| `type=5, jkType=0` + `usebank=1` | ✅ 200 |
| `type=5, jkType=1` + `usebank=0` | ❌ 400 付款凭证科目必填 |

我们此前所有模板的办理节点都是 `jkType=1`，所以这条链路长期处于 skip 状态。
换成 `jkType=0` 后直接跑通——而 `jkType=0` 正是线上「出纳办理」的形态
（218 个真实节点里 `type=5/jkType=0` 有 8 个、`jkType=1` 有 22 个）。

### 实测语义（`tests/h5/test_flow_accounting_cashier.py`，11 条全通过）

**多人会计审批（type=1 / jkType=0）**

- 一人通过 → 保持审批中；两人都通过 → 终态；与顺序无关
- 与 `jkType=1` 的普通审批完成条件一致（有对照用例）
- 同一人重复审批**被接受**（xfail 监控，与会签节点同样的去重缺失）

**多人出纳办理（type=5 / jkType=0）**

- 一人办理 → 保持审批中；两人都办理 → 终态（对应「需所有人出纳办理同意」）
- **同一人重复办理虽被接受，但不能顶替第二个人**（有专门的正向断言 —— 否则一个人
  就能走完需要双人把关的付款环节，这是本模块最值得关注的风险点）
- 非办理人办理被拒；审批未完成时抢跑办理被拒

`lhlh-会计审批多人`、`lhlh-普通审批多人`（对照）、`lhlh-出纳办理`、`lhlh-他人办理`

### 越级 / 抢跑防护（`lhlh-全链路越`）

模板结构：审批[B] → 审批[A,B] → 出纳办理[A,B]，A 是发起人但**不在第一层**。

| 动作 | 期望 | 实测 |
| --- | --- | --- |
| A 在第一层未完成前审批 | 被拒 | 400「不能操作」✅ |
| A 在流程还没走到办理层时办理 | 被拒 | 400「不能操作」✅ |
| B 过第一层、A/B 过第二层、A/B 办理 | 终态 | ✅ 3 条审批 + 2 条办理 |

### 踩到的坑：轨迹有写入滞后，不能逐层断言

详情接口的 `logs` 有短暂写入滞后（操作完立刻读，往往少 1~2 条，连读两次仍是同一份快照）。
所以「有没有跳级」**不能**逐层比对增量——那会把读滞后误判成 bug。
正确做法是**收尾时校验总条数**：实际条数 < 预期条数，才说明某次动作同时推进了多个节点。

> 这条经验对所有依赖审批轨迹的用例都适用。
