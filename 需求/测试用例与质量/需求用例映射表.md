## 3. 组织方式：用例是「按功能写」的

- **目录按功能域**：`tests/h5/`（审批流）、`tests/web/`（web 后台 + 仓库）、`tests/warn/`（预警，再按档位/来源/契约/送达/时期/Worker/台账切）、`tests/contract/`、`tests/unit/`。
- **marker 按功能与层级**：`flow` / `warn_notify` / `warn_mgmt` / `h5_ui` / `crud` / `p1` 等，**没有需求 ID 维度**。
- **`docs/用例总清单.md`** 由 `scripts/gen_case_list.py` 按**文件路径**生成，不是按需求分组。
- **追溯靠文字**：① 用例文件头 docstring 挂 §章节（如 `test_warn_management.py`）；② `tests/warn/README.md` 讲业务链路；③ `docs/测试清单用例映射.md`、`docs/web用例清单.md` 按测试清单条目映射。
- **唯一接近需求驱动的例外**：`docs/预警通知_用例设计_20261109.md` 先按 A~G 验收点分组、定三个独立 oracle，再落成 `tests/warn/`，所以第 2 行覆盖最厚。
- ⚠️ **风险**：没有需求→用例双向矩阵时，「某需求测没测」只能靠人肉 grep；新需求做完人工实测很容易停在「验过了」而不落代码 —— 第 1 节第 4/5/6 行三个空白都是这么来的。

## 4. 维护约定（本次确立）

- 新用例的 docstring **必须挂「需求名 + §章节」**，这是需求维度追溯的最小成本实现。
- 新增/修改用例后**回填本表第 1 节**；`pytest.ini` 已开 `--strict-markers`，新 marker 必须先注册再写用例。
- 「人工实测 PASS」与「自动化覆盖」分列记录，验收报告不替代用例。
- 发版前用 `pytest --collect-only -q` 的实际条数与本表对账一次。
