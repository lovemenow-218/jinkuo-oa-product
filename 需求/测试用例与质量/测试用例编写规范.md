# 测试用例编写规范

拿到产品需求后，按顺序做五件事：拆需求、画功能点、写用例、评估、再写 pytest。每一步做完确认没问题，再做下一步。

本文参考了两篇文章：《测试用例需求覆盖率不是数字游戏》和《测试用例覆盖率（等价类、边界值、场景法）》。两篇都强调一点：覆盖率数字是结果，需求和测试能对上才算数。

## 1. 五个步骤

| 步骤 | 产出 | 通过条件（不满足不做下一步） |
|---|---|---|
| ① 拆需求 | 每条需求一个编号（REQ-xxx），写清输入、处理、预期 | 每条能单独验证，边界清楚；用户确认理解得对 |
| ② 画功能点 | Xmind 功能点结构（模块→子功能→功能点） | 能一眼看出覆盖了哪些、漏了哪些；叶子节点是能验证的具体事 |
| ③ 写用例 | 表格用例，每条标上需求编号和对应的功能点 | 一个功能点分正常、异常、边界、时序写多条；预期写具体值 |
| ④ 评估 | 三个覆盖率数字 + 没覆盖部分的说明 | 需求和用例能互相对上；用户看完确认后才做下一步 |
| ⑤ 写 pytest | pytest 用例（注释里写用例编号和需求编号），并回填执行结果 | 与 `docs/需求用例映射表.md` 保持一致，能顺着需求查到用例和执行结果 |

需求有变更，回到第①步重新看影响范围，同时更新需求表、用例和回归清单。

本项目开发代码由工具生成、没有规格文档。如果拿到需求不拆、不评估就直接写 pytest，跑通了也说不清测的是哪条。生成的用例要人工核对后才能正式用。

## 2. 第①步：拆需求

拿到产品需求，先拆成一条条的，不要在整段文字上直接写用例。每条需求：

- 编号唯一，如 `REQ-SWC-101`，体现层级，方便来回查；
- 一条需求只写一个能验证的点，不把几件事揉一起，也别拆成几十条凑数；
- 写清输入条件、处理逻辑、预期输出。有歧义、问不出边界的，先找产品确认，不写进基线。

例子（原始需求"应能识别并处理油门踏板故障"拆成）：

- `REQ-101` 电压超过 4.8V 时，100ms 内置故障码 P0120 并进入跛行模式；
- `REQ-102` 电压低于 0.2V 时，按同样方式处置；
- `REQ-103` 两路信号差值超过 10% 时报传感器合理性故障；
- `REQ-104` 跛行模式下，电机扭矩限制在最大扭矩的 30% 以内。

## 3. 第②步：画功能点（Xmind）

画脑图是为了防漏，能一眼看出覆盖了哪些。图都放 Xmind，不用表格做发散。

- 画的是被测功能有哪些功能点的结构树（模块→子功能→功能点），不把测试设计维度当主干；
- 叶子节点写到一条用例能验证的具体事，别停在"测一下登录"这种层；
- 每个叶子对应后面表格里的一条或几条用例，表格"关联测试点"列填 Xmind 节点名。

例子：Xmind《消息中心功能点》 https://app.xmind.cn/share/aBlTqDWp （94 个主题，和 `docs/测试用例表头模板.csv` 里的用例逐点对应）。

## 4. 第③步：写用例

### 4.1 一个功能点分四类写

别一个功能点只写一条。用等价类、边界值、状态迁移、场景法展开：

| 场景 | 覆盖什么 | 消息中心的例子（批量已读） |
|---|---|---|
| 正常路径 | 主流程跑通 | 当前门店当前筛选下通知全部标已读 |
| 异常路径 | 失败、超时、重复、脏数据 | 请求失败不误标、重复点幂等 |
| 边界条件 | 0/1/满页/跨页、临界值、超长 | 仅 1 条未读、跨页未读是否全清 |
| 状态/时序 | 状态流转、跨端、并发 | 已读后四处计数同步、跨端已读同步 |

预期写具体值，比如"角标显示 99+""门店2 排在门店10 前""合计按真实值 156 算"，别写"功能正常"。

### 4.2 表头字段

| 字段 | 说明 |
|---|---|
| 用例ID | 唯一编号，如 `TC_MSG_001`，不复用 |
| 所属模块 | 功能归属，对应 Xmind 的一级分支 |
| 关联测试点 | 回溯到 Xmind 叶子节点 + `REQ-xxx` 需求编号，方便来回查 |
| 用例标题 | 一句话说清测什么 |
| 优先级 | P0 阻断 / P1 高 / P2 中 / P3 低 |
| 前置条件 | 执行前必须具备的账号、数据、环境状态，别人照着能搭出同样场景 |
| 测试数据 | 具体输入值（金额按千分位两位小数写，如 `1,100.00`） |
| 操作步骤 | 编号分步，一步一个动作，参数写具体，别写"连接设备采集数据"这种空话 |
| 预期结果 | 写具体值、能判断对错；一条用例一个检查点 |
| 执行结果 | 通过 / 失败 / 阻塞 / 未执行 |
| 执行人 / 备注 | 责任人、缺陷单号等 |

### 4.3 编写要求

- 正反成对：有"能看"就要有"越权看不到"，有"已读"就要有"重复读幂等"。
- 一条用例一个检查点。别把一堆需求挂到一条用例上，跑失败了定位不到是哪条坏，通过了也说明不了那些需求都验过。
- 金额一律会计格式：千分位逗号加两位小数，零写 `0.00`；预警卡片主文案按 11-17 定的口径例外（去括号去货币符号）。
- 生成的用例人工核对三项：步骤能不能照着做、预期能不能判断对错、需求编号有没有挂错。核对记录留下来。

## 5. 第④步：评估

### 5.1 三个数字分开报

| 指标 | 公式 | 含义 |
|---|---|---|
| 设计覆盖率 | 已关联用例的需求数 ÷ 需求总数 | 需求有没有被用例覆盖（设计阶段） |
| 执行覆盖率 | 已执行用例数 ÷ 应执行用例总数 | 用例跑没跑（执行阶段） |
| 通过率 SC/EC | 执行通过用例数 ÷ 已执行用例数 | 系统质量是否合格 |

三个数字分开报，不要混成一个"覆盖率 98%"。用例设计完、映射上，只能叫用例需求映射率，没跑过的用例不算覆盖。

辅助数字：`EC/TC` 看进度；`BC≥FC`，缺陷数一般多于失败用例数，多出来的是靠经验发现的。

### 5.2 三种常见错误

1. 拆需求凑分母：把一条需求拆成几十条细碎项，问拆分依据时答不上来。
2. 一条用例挂满需求：跑失败了定位不到是哪条坏，跑过了也证明不了那些需求验过。
3. 只算设计不算执行：用例躺在评审记录里没跑，就报 100%。

### 5.3 没覆盖的写清楚

没覆盖或没通过的，写清楚哪些没测、为什么不测、风险多大、谁确认的、什么时候补。比如"台架没到位，等台架好了补测，风险高，测试经理已确认"。写清楚原因比硬凑 100% 有用。

### 5.4 用户确认

评估报告（三个数字 + 没覆盖说明 + 未决问题）给用户看，用户说可以了，再做第⑤步。

## 6. 第⑤步：pytest 与对照

`tests/` 下的 pytest 用例是成熟的手工用例转成的自动回归。不是所有手工用例都要转，只转经常回归、功能不再大改的。

- 写 pytest 时，用例编号和需求编号写进注释，和 `docs/需求用例映射表.md` 对齐；
- 跑完回填"执行结果"，失败的关联缺陷单，缺陷单再链回需求编号，让需求、用例、执行结果、缺陷能互相对上；
- 新 marker 先在 `pytest.ini` 注册（已开 `--strict-markers`）。

## 7. 模板文件

- 功能点树：Xmind《消息中心功能点》 https://app.xmind.cn/share/aBlTqDWp
- 用例表：`docs/测试用例表头模板.csv`（消息中心用例，和上面的功能点逐点对应），已加 UTF-8 BOM。

导入飞书：

- 电子表格（想要 Excel 那种单元格）：飞书云文档 → 新建电子表格 → 导入 → 选这个 CSV；
- 多维表格（想要筛选、状态看板、多人协作）：飞书 → 新建多维表格 → 导入 → 选 CSV，字段自动映射。

日常用例管理推荐用多维表格：优先级和执行结果可以做筛选视图，一条用例一行，方便跟踪。
