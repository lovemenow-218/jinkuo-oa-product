# 测试分层说明：单元测试 / 集成测试 / 手工测试

> 回答你的问题：**单元测试和集成测试不是一回事，现在这个项目里两者都有，但以前只有集成测试。**
> 本轮补充后，测试分成三层，各自解决的问题不同。

## 1. 三层对比

| 层级 | 测的是什么 | 要不要环境/网络 | 速度 | 什么时候跑 | 目录 |
| --- | --- | --- | --- | --- | --- |
| **单元测试** | 我们自己写的代码逻辑（HTTP 客户端的响应判定、只读保护、环境切换） | **完全不需要**，用假数据伪造返回 | 毫秒级 | 改代码就跑，随时可跑 | `tests/unit/` |
| **集成测试** | 真实接口是否按预期工作（登录、审批流转、人员查询…） | 需要测试环境地址 + 账号 | 秒级 | 拿到环境后跑 | `tests/h5/` |
| **手工测试** | 界面交互（机型兼容、弱网、键盘遮挡、上传中禁止提交） | 需要真机 | 分钟级 | 发版前专项 | 不在代码里 |

## 2. 为什么必须有单元测试这一层

集成测试的结论**完全依赖客户端的判定逻辑**——客户端负责回答"这次请求算成功还是失败"。

而这个系统有个坑：**兼容接口的业务失败也可能返回 HTTP 200**（`{status:500, success:false}` 但 HTTP 状态是 200）。
如果客户端只看 HTTP 状态码，就会把失败判成成功，于是所有集成用例都会"通过"——**结论全是假的**。

所以这类逻辑必须脱离环境单独锁死：

```
tests/unit/test_http_client.py
  ├─ 兼容包装成功 / 业务失败但 HTTP 200（防"假成功"）
  ├─ 新框架错误体 {ok:false, error:{code,message,requestId}}
  ├─ 会话失效识别：401 与 100101~100103
  ├─ PATCH → POST + X-HTTP-Method-Override
  ├─ 只读保护：写请求本地拦截、白名单、默认值必须为只读
  └─ 请求头组装（Authorization / syOpenAppToken / 开发上下文头）

tests/unit/test_contracts.py
  ├─ 环境切换优先级：--env > JKOA_ENV > active_env
  ├─ 环境不存在 / 地址为空要立刻报错
  ├─ 密码支持环境变量注入
  └─ 自动化自有模板的约定（不依赖会被人工改动的模板）
```

## 3. 各层怎么跑

```bash
# 单元测试：不需要任何环境，随时可跑（换环境前后都建议先跑一遍）
pytest -m unit

# 集成测试：需要环境
pytest --env=test -m smoke      # 冒烟，先确认地址/账号/令牌通
pytest --env=test -m regression # 日常全量（除仓库/进销存以外的一切）
pytest --env=test -m slow       # 耗时/写操作/链路
pytest --env=test -m wms        # 仓库/进销存，独立跑
pytest --env=test -m flow       # 按模块过滤（flow / hr / org …）
pytest --env=test               # 全量（含 UI，会起浏览器）

# 换环境后的建议顺序
pytest -m unit                  # 1. 先确认工具本身没问题（不联网）
pytest --env=test -m smoke      # 2. 再确认环境通
pytest --env=test -m regression # 3. 最后日常全量
```

### 3.1 执行档位（tier）与 CI 对应

五档互斥，每条用例只落一档，由 `conftest.pytest_collection_modifyitems` 自动归档：

| 档位 | 条数 | 内容 | 什么时候跑 |
| --- | --- | --- | --- |
| `unit` | 101 | 纯本地，不联网（客户端判定、只读保护、环境切换） | 改代码就跑 |
| `smoke` | 37 | 环境连通性：登录、基础列表、关键只读接口 | 工作日 10:07 |
| `regression` | 775 | h5 + web 日常回归（含 contract / warn / ui 的只读部分） | 工作日 16:07 |
| `slow` | 44 | 耗时、写操作、链路串联 | 发版前 / 手动 |
| `wms` | 742 | 仓库 / 进销存（`warehouse` 标记自动归此档） | **不排定时**，需要时才跑 |

归档规则（未显式打档位标记时）：`warehouse` → `wms`；`ui`/`ui_write`/`h5_ui`/`chain`/`crud` → `slow`；其余 → `regression`。
仓库/进销存之所以独立，是因为这套功能平时没人动，混在 regression 里既拖慢日常又容易被当成"长期红"；独立后红色一眼能认出归属。

本机定时派发（`scripts/install_launchd_dispatch.sh`）只装 smoke / regression 两档（工作日 10:07 / 16:07）。

`wms` **没有任何定时**：GitHub 侧没有 cron，本机也不派，平时完全不动（这块开发侧没人维护，接口漂移和 403 常年存在，跑出来的红点没有信号价值）。需要时手动触发一次即可：

```bash
scripts/ci_dispatch.sh wms      # 立刻派一次（自己终端里跑）
```

或在 GitHub 页面 Actions → `pytest` → Run workflow → `tier=wms`。CI 里 `wms` job 仍然保留，只是只能被 `workflow_dispatch` 的 `tier=wms` 命中。

## 6. 首次在新环境运行人事/企业管理的注意事项

这两个模块的用例是**先写好、尚未执行**的（按你的要求换地址前不运行）。断言都做了
"结构存在性"级别的容错（空数据集视为合法），但仍建议首次按模块单独跑并校准：

```bash
pytest --env=test -m hr -v
pytest --env=test -m org -v
```

常见校准点：
1. 人员/部门字段名可能不同（如 `staff_name` vs `name`）→ 按返回调整
2. 若接口不支持 `shop_id` 过滤 → 用例会自动 skip 并给出说明
3. 空数据集的门店会跳过隔离类断言，属正常
