### 0.1 ⚠️ 登录入口：初版写错了，这里是实测结论

第一版我根据前端产物写了 `/api/v1/auth/login`。**用假凭据实测后确认这条路由不存在**：

| 路径 | 实测结果 | 结论 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | `404 {"error":{"code":"NOT_FOUND","message":"Route not found: /api/v1/auth/login"}}` | **不存在** |
| `POST /base_passport/passport` | `400 {"message":"handleType is required"}` | **这才是登录接口**，需要 `handleType` |
| `POST /base_passport/passport` + `handleType=login/pwd/password/sms` | 全部 `400 "Unsupported handleType"` | `handleType` 是**白名单校验**，✅ **取值已破解，见 §0.1.1** |
| `POST /auth` / `/api/open/auth` | `200 {"status":200,"success":true,"data":{"token":"","openid":""}}` | 存在，返回空 token（legacy 包装） |

**由此产生的三个待办**：

1. ~~需要开发提供 `handleType` 的合法取值~~ → ✅ **2026-10-12 已自行破解**，共 3 个：
   `MobilePwdLogin` / `OrgAdminPwdLogin` / `OrgStaffPwdLogin`（详见 §0.1.1）。**不再是阻塞项**。
2. **为什么前端会调一个不存在的路径**：前端把它的常量命名为 `AUTH_SERVE_*`（`AUTH_SERVE_LOGIN` / `AUTH_SERVE_REFRESH_TOKEN` …），
   即**独立的认证服务**；而这套服务**没有部署在 `oacs.fzjinkuo.com`**（连同 `/api/v1/talk/*` 等 105 条 IM 接口一起 404）。
   详见 §0.4.2。所以 web 前端实际连**两个后端**，你给的接口文档只覆盖了其中一个。
3. 初版文档里写的 `/api/v1/auth/refresh-token`（我据此设计了 W-PERM-09/10 的"登出后可无限续期"风险）
   **同样不存在**。**注意：W-PERM-09/10 不要删** —— 那条风险本身依然成立，只是要改用**实际存在的令牌机制**去验证
   （先按 §0.3 确认 `AUTH_MODE`，再定位真实的登出/续期接口）。

### 0.1.1 ✅ 登录协议已完全破解 + 门店隔离方案（2026-10-12 三修）

用户提供了真实登录抓包，结合登录页源码 `assets/login-Zq6lkGao.js` 与实测，
**登录链路与门店锁定机制全部确定**。

**（1）`handleType` 只有 3 个合法值**

| handleType | 触发条件 | 是否需 `temp_token` | 说明 |
| --- | --- | --- | --- |
| `MobilePwdLogin` | 用户直接输手机号+密码点登录 | 否 | 登录流程**第一段**，`business_id` 传 0 |
| `OrgAdminPwdLogin` | 门店列表项 `acc_role_type == "sy-org-admin"` | **是** | 第二段，落到指定门店（管理员身份） |
| `OrgStaffPwdLogin` | 门店列表项 `acc_role_type == "sy-org-staff"` | **是** | 第二段，落到指定门店（员工身份） |

来源：`login-Zq6lkGao.js` 的 `loginBusinessCheck(n)` 与 `passportHandle2(n, r)`；
主包 `index-CmUHnjLe.js` 里这两个常量各出现 1 次（用于登录后的门店切换）。

**（2）两段式登录时序**（这是 h5 侧没走完的分支，h5 `conftest._login` 遇到 `chain` 就报错）

```
① GET  /base.base_passport/login_code_need?account_mobile=xxx
   → {"status":200,"data":{"is_need":"off","need_code":"off"}}      ← 实测不需要图形验证码
② GET  /base.base_passport/login_code_data?account_mobile=xxx
   → {"status":200,"data":{"key":"","img":""}}                      ← 需要时才有值
③ POST /base_passport/passport
   {handleType:"MobilePwdLogin", account_mobile, business_id:0,
    account_password, captcha_code:"", captcha_key:""}
   ├─ result_type="alone" → result_data 直接含令牌，单门店账号到此结束
   └─ result_type="chain" → 返回 result_data=**该手机号名下的全部门店列表**
                            + result_token=**一次性票据 temp_token**
④ POST /base_passport/passport
   {handleType:"OrgAdminPwdLogin"|"OrgStaffPwdLogin",
    account_mobile: <门店项里的 account_mobile_show>,   ← ⚠️ 不能用③填的手机号
    business_id: <目标门店>, account_password,
    captcha_code:"", captcha_key:"", temp_token: <③的 result_token>}
   → 令牌 + accountInfo（含 business_id / staff_id / acc_role_type）
```

三个易踩的坑：
- ④ 的 `account_mobile` 必须用门店列表项的 `account_mobile_show`（前端就是这么写的）；
- 密码**明文**传输，前端无 md5/加密（`login-Zq6lkGao.js` 中 `md5`/`encrypt` 出现 0 次）；
- `temp_token` 是一次性的，抓包里的旧值复用会失败。

**（3）门店隔离 —— 回答"能不能只进这家测试门店"：能，靠三层锁**

测试账号 `17633657063` 名下**同时挂着真实门店和测试门店**，
④ 的 `business_id` 一旦取错，测试就会写进真实企业的数据里。因此：

| 层 | 机制 | 落地位置 |
| --- | --- | --- |
| ① 前端既有事实 | 主包硬编码 `const Rte = Object.freeze([200242])`，只有 200242 会解锁额外路由组（报表模块）——**200242 就是官方测试门店** | 逆向所得，非我们发明 |
| ② 登录期护栏 | 白名单 `ALLOWED_BUSINESS_IDS = {200242}`；chain 列表里找不到白名单门店就**抛错中止，绝不选别的**；命中多个也中止；登录后再复核一次 `accountInfo.business_id` | `common/web_api.py`：`_pick_business` / `login_web` |
| ③ 会话期护栏 | 登录态下唯一的跨门店入口 `POST /organize_sys/base/change` 被**显式禁用**（调用即抛错）；另有用例级 fixture `web_biz` 每次进入都复核会话仍在 200242，抓住漂移 | `WebApi.switch_business` / `conftest.web_biz` |

补充：请求头固定带 `x-business-id: 200242`（测试环境允许），
并沿用项目既有的 `read_only` 保护 —— 写操作需显式关闭才会发出。

**（4）登录已端到端跑通；同时纠正我上一轮的一个错误结论**

上一轮用 `curl` 连试两次都拿到 `Password is invalid`，据此下了
"123123 可能是短信验证码、一次性已失效"的结论 —— **这个结论是错的**。
改用 Python `requests` 重放同样参数，**一次就成功**。差异只可能出在
curl 手工拼包或服务端短暂的登录风控上，与密码本身无关。

教训记在这里：**"两次失败"不等于"凭据无效"**。同一个 400 文案
（`Password is invalid`）既可能表示密码错，也可能表示票据过期或触发风控，
单靠错误信息**不能做排他性推断**；换一种调用方式复测再下结论。

### 0.2 两套响应包装（影响所有断言写法）

| 类型 | 结构 | 覆盖接口 |
| --- | --- | --- |
| 新框架 | `{"ok": true, "data": {}}`；错误 `{"ok":false,"error":{"code":"NOT_FOUND","message":"...","requestId":"..."}}` | 健康检查、示例、个人空间大部分 JSON 接口，以及**所有 404 / 校验失败** |
| legacy（兼容层） | `{"status": 200, "success": true, "msg": "", "data": {}}`；列表额外返回 `page/pagesize/pagemax/total` | 财务、组织、经营报表、云商店、OA 兼容接口（`/auth` 已实测为这种） |

> **对测试客户端的影响**：现有 `common/http_client.py` 的 `_check_business` 是按 legacy 的 `status` 判定的。
> 接 web 时必须同时识别 `ok` 包装，否则 `/api/*` 系列接口的失败会被当成"没 status 字段"而放过 → **测试结果会失真**。
> 对应改造用例 W-UNIT-01～03（见 §7.4）。
>
> 另外文档明确警告：**个别历史兼容接口即使业务失败也返回 HTTP 200**，调用方必须同时判断 `success`、`status`、`msg`。

### 0.3 认证与越权测试的可行性（重要）

文档「身份认证和业务上下文」一节给了几条对测试极其关键的信息：

| 文档原文要点 | 对测试的意义 |
| --- | --- |
| 令牌优先级：`Authorization: Bearer` > `syOpenAppToken` > `Cookie: jkoa_token` | web 用 Cookie，h5 用 `syOpenAppToken`，**同一套令牌两处通用** → 跨端越权可测 |
| **`AUTH_MODE=disabled` 时仅解析 payload，不校验签名** | **若测试环境是这个模式，任何人可伪造 JWT 冒充任意员工**。这是本轮最高价值的探测点（W-PERM-29） |
| `x-account-id` / `x-business-id` / `x-staff-id` **开发和测试环境才允许** | 测试环境可用这些头做**跨店/冒名越权**实验（h5 侧此前是"服务端忽略"，需复核是环境还是实现） |
| 生产环境三个上下文值**必须来自令牌声明** | 生产不能靠请求头越权 —— 这条决定了缺陷定级 |
| 公开分享仍受总开关/分享令牌/密码约束；OnlyOffice 依赖短期会话令牌 | 个人空间 63 个未引用接口的越权面，见 §7.2 |

| **`/api/v1/*`** | **105** | **在本机全部 404 `Route not found`**。含 `auth/login`、`talk/*`（聊天）、`contact/*`（通讯录）、`group/*`（群）、`note/*`（笔记）、`upload/*`、`users/*`、`organize/*`、`emoticon/*` |
| `/oa_sys/*` | 6 | `app_push/test`、`oa_flow_pay`、`oa_flow_form_rel`、`warehouse_home`、`warehouse_profile_options`、`warehouse_profiles` |
| `/im_sys/*` | 3 | 与 `/api/v1/talk/*` 同属 IM |
| `/z_jinkuo_ysd/*` | 3 | `excel_import`、`excel_map`、`excel_salary`（云商店导入） |
| `/opentest/*` | 2 | `getOrgTree`、`switchUser` |
| `/base_passport/*` | 1 | `scan_login/scanQrcode`（扫码登录） |
| `/finance_zt/*` | 1 | `voucher_shenhe` |

**这解释了两件事**：

1. **为什么 `/api/v1/auth/login` 会 404** —— 它不是"接口坏了"，而是**属于另一个服务**。
   前端把它的常量命名为 `AUTH_SERVE_*`（独立的认证服务），而这个服务**没有部署在 `oacs.fzjinkuo.com`**。
   换言之 web 前端连的是**两个后端**：文档覆盖的 jk-oa，和一套**未文档化的 IM / 认证服务**。
2. **`/opentest/switchUser` 不是活的后端后门** —— 实测返回的是 SPA 的 HTML 外壳（前端路由回退）而非接口响应，
   说明本机没注册这条路由。但**前端代码里确实引用了它**，仍值得让开发确认是否在别的环境部署（W-API-28）。

> **对测试范围的影响**：本清单 250 条用例覆盖的是**文档这一套后端（jk-oa）**。
> IM / 认证那 105 条属于另一个服务，**不在本次范围内**，需要单独要一份接口文档。

### 0.5 关于「后台菜单出不来」

路由表里**只有少数菜单**带 `apiPermissions` 声明（如 `概览`、`组织架构` 都是 `GET@/`），
菜单的实际可见性由服务端 **`menu_all` + `rbac_my`** 决定。
所以「菜单出不来」有三种可能，**需要分开验证，修法完全不同**：

| 可能 | 验证方法 | 修法 |
| --- | --- | --- |
| A. 账号没被赋角色/权限 | 调 `rbac_my`、`role_all` 看返回 | 配角色即可 |
| B. 菜单配了但接口被拒 | 直接调对应业务接口看是否 403 | 配接口权限 |
| C. **菜单藏了但接口没挡**（最危险） | 无菜单的账号直接调业务接口 → 若返回 200 就是缺陷 | 后端加鉴权 |

> **C 是本次 web 测试的头号目标**：它意味着"看不见菜单"只是障眼法，实际数据全能拿到。

### 0.6 关键发现：全站只有 9 个细粒度权限点，且集中在三个地方

前端路由里带 `isRbac:!0`（细粒度操作权限标记）的节点**一共只有 9 个**：

| 权限点 name | 中文名 | 归属模块 |
| --- | --- | --- |
| `flow_manage_type_add` | 创建审批类型 | 审批类型 |
| `flow_manage_type_edit` | 编辑审批类型 | 审批类型 |
| `flow_manage_type_delete` | 删除审批类型 | 审批类型 |
| `flow_manage_type_copy` | 复制审批类型 | 审批类型 |
| `flow_manage_group_add` | 新增分组 | 审批类型 |
| `flow_manage_group_edit` | 编辑分组 | 审批类型 |
| `flow_manage_group_delete` | 删除分组 | 审批类型 |
| `system_app_version` | APP版本管理 | 系统 |
| `org_sys_rbac_sett` | 权限设置 | 组织 |

**读出来的三点结论**：

1. **权限粒度只做在了「审批类型管理」这一个模块**（7/9）。说明团队有能力做细粒度权限，但**没有铺开**。
2. 其余 40 多个菜单（**含全部审批、工资表、账簿、组织架构这些敏感模块**）**没有任何操作级权限点** ——
   员工能看到菜单，就能做该页面上的所有操作（新增/编辑/删除/导出），**页面内不区分权限**。
   这是本次 web 测试最值得挖的方向，对应 W-PERM-23～26。
3. `APP版本管理` 是唯一带 `isRbac` 的一级菜单 —— 反过来说，**其他一级菜单连"能不能进"都没有独立开关**，
   完全依赖服务端 `menu_all`。

由此推出权限用例的两个设计前提：

- **「菜单不显示」≠「进不去」**。路由在前端包里一直存在，用户直接敲 URL 能不能进，取决于前端有没有统一守卫（W-PERM-03）。
- **即使前端挡住了页面，接口仍可能没挡**。页面只是个壳，数据在接口上 —— 这是 W-PERM-04/05 要验的，**比上一条重要得多**。

## 2. 权限与菜单专项（P0，当前阻塞点，优先做）

> 这一组直接对应你遇到的「菜单出不来」，也是 web 端风险最高的一块。
> 编号 `W-PERM-*`

| 编号 | 场景 | 预期 | 优先级 |
| --- | --- | --- | --- |
| W-PERM-01 | 用当前账号调 `menu_all` | 返回该账号角色应看到的菜单树；与截图一致 | P0 |
| W-PERM-02 | 调 `rbac_my` 与 `menu_all` 比对 | 两者口径一致（不该出现"菜单有、权限没有"或反之） | P0 |
| W-PERM-03 | 无菜单权限的账号**直接输 URL** 访问 `/people_manage/payroll` | 前端应拦截并提示无权限，**不能渲染出页面** | P0 |
| W-PERM-04 | 同上，但**直接调后端接口** `profit`、`kpi_pay` 等 | 后端应返回 403/明确拒绝，**不能返回数据** | P0 |
| W-PERM-05 | **菜单藏了但接口没挡**（§0.1 的 C 类） | 任一菜单不可见的账号，其对应接口必须也拒绝 | P0 |
| W-PERM-06 | 路由声明的 `apiPermissions` 与实际鉴权比对（如 `概览=GET@/`） | `GET@/` 这种宽泛声明不应成为放行依据 | P0 |
| W-PERM-07 | 改角色（`rbac/sett`）后，菜单是否实时变化 | 重新登录或刷新后应立即生效，无旧权限残留 | P0 |
| W-PERM-08 | **降权后旧 token 是否仍带旧权限** | 降权应立即失效，旧 token 不得继续访问 | P0 |
| W-PERM-09 | 登出后调 `refresh-token` 能否换发新 token | 应拒绝。h5 缺陷 2 是"登出令牌仍有效"，web 多了 refresh，**风险被放大** | P0 |

### 9.2 ⚠️ 推翻 2026-10-15 的错误结论

#### ⛔ 本轮最大的坑：`time.time_ns() % 10000` 不是唯一键

第一版用例用 `f"...-{time.time_ns() % 10000}"` 生成 `requestKey`，结果 **9 条里 6 条偶发失败**，
且「单独跑通过、一起跑失败」。根因：

> 1 微秒 = 1000ns，**任何整微秒的调用间隔都是 10000ns 的整数倍**，
> 所以 `ns % 10000` 的结果几乎恒定 —— 同一进程内后续请求全部撞上服务端
> `requestKey` **幂等**，直接回读上一张单据。
> 表现极隐蔽：新建的申购单 `status=已驳回`、`version=3`，
> 于是「创建人自驳」返回 409「审核环节已变化」（它确实变化过，只是不是这张单变的）。

修法：`uuid.uuid4().hex[:12]` 做后缀（见 `_key()`），并在 `_new_requisition` 里
**建完立刻校验状态是「待审核/草稿」**，把幂等回读当场挡住。

#### 另外两个"不是缺陷"的前置条件（别再误判）

- **未付款不能发货**：409「订单付款尚未全部确认，且未开通赊销」是业务前置，
  不是 bug。用例里加 `_ensure_paid()`：本账号登记 → **另一个账号** `confirm`
  （自建自确认不生效），过账后 version 会跳（实测 9→11），发货前必须重读。
- **过账后账面有一拍延迟**：库存/流水断言统一走 `_stock_wait()` 轮询，别写完立刻断言。
